# Codex 执行工作流：后端扩展机制学习项目

## 0. 任务定位与启动方式

这是交给 Codex 阅读并执行的任务书，不是 shell 脚本，也不是已经实现的项目。

本任务书面向希望串起注解、接口实现、Spring扩展点和线程池的Java后端学习者。请通过一个逐步演进的 `operation-log-lab` 项目帮助用户学习，而不是一次性生成最终代码。

学习主线：业务需求 → 找到扩展点 → 编写配置或实现 → 注册和装配 → 被框架调用 → 测试验证。

核心问题：我提供了什么？谁使用它？什么时候使用？怎样接入？失败时怎么办？

首次启动指令：

    请完整读取 CODEX_WORKFLOW.md，检查当前工作区，只执行 M0。
    请实际创建文件并运行可运行的检查，不要只给建议或贴代码。
    本轮不要提前实现 M1—M6。完成 M0 后按任务书交付并停止。

后续每轮只推进一个里程碑。里程碑不是一次提交或一个固定时间段，而是具有明确验收条件的一组工作。

## 1. 项目目标与范围

最终交付一个学习用操作日志组件。对受管理的业务方法标注 `@OpLog` 后，通过 Spring AOP 采集操作名称、方法标识、执行耗时、成功或失败状态与异常类型，再将不可变日志记录提交到专用执行器，由 `LogSink` 输出。

主链路：业务调用 → Spring AOP 代理 → 日志切面 → 业务执行 → 构造记录 → 显式提交给 logExecutor → 工作线程调用 LogSink。

先实现同步记录，再单独学习原生线程池，最后组合为异步记录。`@Async` 放在独立对照示例中，不对主链路再做一层异步提交，避免一条日志被处理两次。

这是学习用的尽力记录组件，不是可靠审计系统。采用内存队列，不承诺进程崩溃后保留未处理记录，也不承诺重要日志绝不丢失。队列拒绝和输出失败必须可观察。

不引入数据库、Redis、消息队列、真实登录、支付、邮件、分布式追踪、前端界面、手写线程调度器或自定义 Starter。暂不实现全面的注解组合、继承和桥接方法兼容。

## 2. 环境与安全边界

开始修改前读取当前目录和父目录中适用的 AGENTS.md / AGENTS.override.md，检查项目结构和 Git 状态。不得覆盖用户未提交的改动，不得执行 reset --hard、clean -fd、强制推送或删除已有业务文件。

若当前目录只有本任务书、Git 元数据等初始化文件，就在当前目录创建学习项目。若已有本学习项目，则恢复进度，不要重建。若当前目录是其他已有项目，默认在 `examples/operation-log-lab/` 创建独立示例，不修改宿主项目的构建、依赖和业务实现；在交付时明确后续工作目录。

新项目优先使用 Java 21 和 Maven。只有 Java 17 可用时可选择 Java 17，并说明选择。不要为满足偏好而升级或改写用户的系统 JDK。Spring Boot 选择与实际 JDK 兼容的正式版本，固定完整版本号；通过官方资料或已验证的既有构建核实，不使用 SNAPSHOT、动态 latest 或凭空编造的版本号。

测试使用所选 Spring Boot 版本管理的 JUnit Jupiter 等测试组件，不独立强锁互不兼容的测试库版本。只按阶段添加必需依赖，优先使用官方推荐坐标。暂不使用 Lombok，保留学习者可直接阅读的代码。

网络、文件写入、依赖安装和命令执行必须遵守当前 Codex 权限。不得关闭沙箱、规避审批、索取真实密钥或连接生产服务。缺少权限、JDK或无法获取依赖时记录阻塞；可以完成安全的文档和静态检查，但不得把未运行的构建标成成功。不要反复重试同一个环境错误。

不自动提交、推送或创建远程 PR。用户明确要求时，再执行对应操作。

## 5. M0：环境检查和可运行骨架

目标：建立一个能执行测试的最小 Spring Boot 项目，并保存后续工作规则。

任务：检查工作区、工具链与权限；确定独立学习项目位置；创建第 3 节的文档和最小构建。新项目暂时只需要 Web 和测试相关依赖，AOP 在后续阶段添加。包名使用 `com.example.operationloglab` 或与既有学习项目一致的名称。

实现最小应用入口以及 `GET /demo/ping`，返回固定的 `ok`。建立启动上下文测试和一个真实验证 HTTP 映射的测试。不得只 mock 掉控制器再断言 mock 的返回值。

能够生成并验证 Maven Wrapper 时使用它，并在文档中记录 Unix 与 Windows 的对应命令。无法生成 Wrapper 但系统 Maven 可运行时，允许使用系统 Maven完成本阶段，明确记录回退方式；不得制作假的 Wrapper 脚本。

验收：实际构建与测试成功，接口映射可验证，README 给出与环境一致的测试和启动命令，M0 证据被保存。没有可用环境时标为 BLOCKED，不提前开始 M1。

本阶段不要创建 OpLog、切面、日志线程池或最终业务组件。

## 6. M1：接口、多态与 Spring 装配

目标：理解“自己的实现通过接口交给调用者使用”。

任务：定义不可变的 `OperationLogRecord` 与 `LogSink` 接口。记录仅包含操作名称、方法标识、耗时、成功状态和可选异常类型等必要信息，不收集方法参数、返回对象或异常消息中的敏感数据。

提供使用日志框架输出的 `ConsoleLogSink`，以及仅供测试使用的线程安全 `InMemoryLogSink`。编写最小 `OperationLogService`，通过构造器依赖 `LogSink`，此阶段同步调用。

分别展示纯 Java 中手动传入实现和 Spring 中注册并注入实现。测试实现与正式实现不能造成不明确的 Bean 注入；在测试作用域内明确选择实现。

验收：相同调用方能使用不同 LogSink；无需修改调用方业务逻辑即可替换输出实现；测试能够检查真实保存的记录；Spring 容器装配测试通过。

学习问题：接口规定什么？实现类负责什么？纯 Java 与 Spring 场景中分别是谁创建并注入对象？

## 7. M2：自定义注解和反射读取

目标：区分“声明信息”和“处理信息”。

任务：定义仅用于方法的 `@OpLog`，包含必填操作名称，设置运行时保留。先不写 AOP。通过一个普通反射示例读取测试方法上的注解与属性，将读取到的信息交给明确编写的处理代码。

验收：能读取被标记方法的操作名称；未标记方法得到无注解结果；只给方法加注解而不调用任何处理器时，不会自行增加日志记录。这些行为要由测试表达，而非仅在文档里声明。

学习问题：注解本身保存什么？反射示例中的哪一行读取它？是谁触发了反射示例，而不是注解主动执行了代码？

边界：不引入 AOP、不异步、不实现通用注解扫描框架。

## 8. M3：AOP 驱动的同步日志

目标：把 M2 的声明信息接入 Spring 方法调用流程。

任务：添加与实际版本兼容的 AOP 依赖，定义 `OperationLogAspect` 和受 Spring 管理的 `DemoOrderService`。通过外部 Bean 调用被标记的公开方法，模拟成功和业务抛异常两种情况，不执行真实下单或支付。

环绕通知中只执行一次业务方法，使用适合计算经过时间的时钟测量耗时，构造记录后同步调用日志服务。不改变成功返回值，不包装或替换原始业务异常。日志输出的普通失败不得覆盖业务结果或原始业务异常；不能吞掉严重 Error。

本阶段只保证对“实现类公开方法直接标注 OpLog，且调用经过 Spring 代理”的约定成立。明确记录其他注解位置的支持边界。

验收：成功调用恰好记录一次；业务异常也恰好记录一次且原异常被保留；未标注的方法不记录；能够验证记录内容与业务调用对应；存在日志输出故障的测试。

另外编写一个隔离的自调用对照测试：从代理外部调用被标记方法，以及同一个目标对象内部直接调用该方法，分别观察增强行为。该例子用于理解代理边界，主示例不要依赖有问题的自调用路径。

文档使用文本调用链与真实类名解释“谁识别注解、谁执行切面、谁调用业务方法”。

## 9. M4：原生线程池与扩展接口

目标：先不依靠 Spring，直接理解任务执行、排队和拒绝。

任务：在独立练习与测试中创建 `ThreadPoolExecutor`。教学参数：核心线程数 2，最大线程数 4，有界队列容量 3；明确空闲时间和时间单位。参数仅用于实验，不作为生产容量建议。

实现具有可辨认名称的 `ThreadFactory`。先使用抛出异常的拒绝策略观察行为，再实现一个计数后仍明确拒绝的 `RejectedExecutionHandler`，用于理解接口回调。不要使用静默丢弃策略。

确定性实验：在工作线程创建成功、线程池处于运行状态且任务都被同步器阻塞而未完成的前提下，提交 7 个任务，验证最多已有 4 个工作线程执行、3 个任务排队；第 8 个提交应触发明确拒绝。使用线程工厂计数、任务开始信号和队列观察等证据，不依赖打印先后顺序或固定睡眠时间。

再释放任务并验证全部已接收任务能够完成，关闭后不再接受新任务。提交为 Future 的失败任务要实际读取失败结果，不要把异常藏在未读取的 Future 中。

验收：执行、排队、拒绝、异常观察、关闭路径均有测试；每个测试都有超时与资源释放；能够解释 ThreadFactory 和拒绝处理器分别在什么时机被调用。

此阶段不改造 M3 的同步日志主链路。

## 10. M5：把日志与专用线程池组合起来

目标：串起“注解声明 → AOP 处理 → 任务提交 → 线程执行 → 接口输出”。

任务：创建受 Spring 管理的专用 `ThreadPoolTaskExecutor`，明确命名为 `logExecutor`，配置有界队列、可辨认线程名前缀以及明确拒绝策略。通过构造器与限定名称注入，主链路显式调用执行器提交不可变的 OperationLogRecord。

主链路只走一次异步提交。业务方法成功并不等于日志输出成功；单独记录提交拒绝次数与已接收任务的输出失败次数，并通过安全的本地诊断或测试查询暴露。拒绝与日志写入的普通失败不改变原业务结果，也不能静默消失。不记录敏感参数。

不能在业务请求链上调用 Future.get、join 或等待日志写完，否则无法体现异步隔离。测试可以使用有界等待观察异步结果。

对照示例：单独创建 `@Async("logExecutor")` 的演示 Bean，启用所需配置并通过另一个 Bean 调用它。示例选择有返回 Future 的方式，展示异步异常的观察方法，以及同对象直接调用的差异。不得让这个示例再次处理主链路中的同一条日志。

验收：使用真实 Spring 代理和真实执行器验证一次业务调用只产生一条日志；LogSink 的执行线程与调用线程不同且名称匹配；用同步器阻塞 Sink 时业务方法仍可返回；业务异常仍保留；拒绝和输出失败都能被观察。保留对同步行为的独立组件测试，不要求同步集成测试仍按原时序工作。

学习文档明确区分自定义 OpLog、Spring 自带 Async、原生 ThreadPoolExecutor 与 Spring 执行器适配组件的职责。

## 11. M6：配置、关闭、回归与知识迁移

目标：让组件行为可配置、边界可解释，完成一次完整验收。

任务：使用项目版本支持的配置绑定方式，将 `oplog.enabled`、核心线程数、最大线程数、队列容量、线程名前缀和关闭等待时间集中管理。初始默认值沿用教学实验范围，不宣传为生产最佳实践。

定义并测试配置约束，例如核心数不得大于最大数、容量应符合本项目选定的边界、等待时间不得为负；非法配置应在初始化时明确失败，而不是运行后出现难以定位的故障。

禁用日志时不提交日志任务，也不影响业务方法。容器关闭时，按有界策略处理已接收任务并等待线程退出；明确超时后不能保证未完成任务持久化。用隔离上下文和可释放的测试任务检验关闭，避免测试线程泄漏或永久挂起。

补齐成功、业务失败、日志失败、过载拒绝、关闭期间提交和禁用等路径的回归测试。不要把所有组件都 mock 掉。执行完整测试以及构建配置中已经存在的静态检查；没有配置的工具应如实写“不适用”，而不是宣称 lint 通过。

在 `docs/lessons/M6.md` 整理迁移表：组件、配置或接口/注解、注册入口、实际调用者、触发时机、失败策略、对应测试位置。覆盖 OpLog、切面、LogSink、线程工厂、拒绝处理器与执行器。

仅在文档里提出一个不自动实现的迁移练习：按照同样的五个问题分析一个自定义参数校验器或 MVC 拦截器。不要把额外功能并入本轮。

    先核对当前源码和最近的测试结果，再只推进下一个未 VERIFIED 的阶段。
    如果当前阶段 BLOCKED，优先处理或报告阻塞，不越过验收。
    如果上一阶段学习验收尚未完成，将其标为 SKIPPED，不写成已掌握。
    实际实现、测试、更新文档，按第 12 节交付后停止。

### 看懂当前阶段

    只讲解当前已实现阶段，不修改代码，不进入下一阶段。
    从实际入口沿调用链说明：谁创建、谁注册、谁调用、何时触发、如何处理失败。
    选两个关键文件结合真实代码解释，最后给我三个问题，不先给答案。

### 检查我的练习

    根据我的回答或工作区改动，检查本阶段学习目标是否达到。
    区分概念误解、代码错误和尚未验证的行为。可以运行相关测试。
    不替我完成练习，不修改业务代码，不自动进入下一阶段。
    如实更新学习状态，并给出一个最小改进方向。

### 新会话恢复

    这是已有的 operation-log-lab 项目，请不要重新生成或覆盖它。
    读取 AGENTS.md、CODEX_WORKFLOW.md、docs/PLAN.md 和 docs/PROGRESS.md。
    检查当前改动和测试证据，先总结实际进度及阻塞，再继续当前未完成阶段。
    若阶段已完成，只推进一个下一阶段。按任务书交付后停止。

### 独立审查

    作为审查者检查本学习项目，先不要修改代码，也不要扩大功能范围。
    对照任务书和实际 diff，重点检查：代理边界、重复日志、原始异常保留、
    线程池队列边界、拒绝与异步异常的可观察性、配置约束、关闭行为、
    敏感数据泄漏，以及测试是否真正验证了 Spring 代理和异步执行。
    对每项发现给出严重程度、文件位置、触发条件和验证方法。
    没有发现明确问题时如实说明，同时列出没有验证的边界。
